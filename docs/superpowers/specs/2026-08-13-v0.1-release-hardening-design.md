# V0.1 Release Hardening Design

Date: 2026-08-13
Base: `main` at `5d2f6b5618450f8b872271514658befee6b2c95d`
Target: `v0.1.0`

## Goal

Turn the verified source app into an installable Windows x64 release that needs no separate Python install, while preserving the full V0.1 workflow: Capture -> Calibrate -> Detect/Edit -> Measure -> Arrange -> Generate -> Save/Export.

This phase hardens and packages V0.1. It does not add V0.2 product features.

## Distribution

Use PyInstaller in one-directory/windowed mode, wrapped by Inno Setup.

Artifacts:
- `ToolDrawer-Studio-0.1.0-Setup.exe`
- `ToolDrawer-Studio-0.1.0-Portable.zip`
- `SHA256SUMS.txt`

The installer is per-user by default, creates a Start Menu shortcut, offers an optional desktop shortcut, and never deletes user-created projects or exports outside the install directory. No auto-updater or `.tds` file association is required for 0.1.0.

## Version authority

`0.1.0` is the canonical app version. One version source drives package metadata, installer version, artifact names, runtime version display where present, and release-tag checks. CI fails if tag and application version disagree.

## Frozen runtime

Add one focused runtime/resource-path helper for source-vs-frozen behavior. Packaging must include the pieces required by PySide6/Qt, OpenCV, NumPy, Shapely, CadQuery/OCP, QR generation, and ToolDrawer Studio modules/resources.

The built application must be tested on a clean Windows CI runner. Source tests alone are not enough.

## Smoke/self-test

The frozen executable gets a noninteractive self-test entry point for CI. It must initialize Qt in noninteractive/offscreen mode, import critical dependencies, create Shapely/CadQuery geometry, generate one foam organizer and one Gridfinity organizer, and export STEP/STL/DXF to a temporary directory. Failure returns nonzero with a useful diagnostic.

## Diagnostics

Write local application logs under the current user's application-data area, outside the install directory. Unhandled exceptions record timestamp, app version, platform information, and traceback. Logs do not dump project images or complete project contents by default.

Normal validation failures remain user-facing application errors rather than crash events.

## Unsaved-project protection

Track whether editable project state differs from its last save/open baseline. Before opening another project, beginning a new imported project, or closing with unsaved edits, present Save / Discard / Cancel.

Cancel preserves the current project. Failed/cancelled Save does not continue the destructive action. Generated-CAD currentness remains separate from editable-project dirty state.

## Recent paths/preferences

Persist lightweight per-user preferences outside `.tds` files:
- bounded recent-project list;
- last project open/save directory;
- last manufacturing export directory;
- last photo-import directory where practical.

Missing recent files are removed or ignored gracefully. Preferences store paths/settings only.

## Long operations

Generate and export must show an explicit busy state, disable conflicting actions while active, restore controls after success/failure, preserve stale/current rules, and show concise user-facing failures while detailed diagnostics go to the log. Use indeterminate progress instead of invented percentages where no truthful progress value exists.

## Camera/network resilience

The app must still launch and support imported-photo/offline workflows when cameras are absent/busy, camera enumeration fails, no private LAN address is available, phone capture cannot start, or network interfaces change. These are recoverable feature failures, not startup failures. Normal organizer work requires no internet connection.

## Deterministic manufacturing fixture

Add a known-geometry release fixture covering multiple tools, multiple pocket depths, translated/rotated placements, manufacturing clearance, a grab-side scoop, foam output, multi-cell Gridfinity, magnets, optional M3 screw geometry, stacking-lip behavior, and STEP/STL/DXF export.

Automated checks assert known dimensions, floor/depth relationships, expected features, valid final solids, and nonempty exports.

## Physical validation

Release documentation includes a real-world checklist: capture/calibrate several tools, detect/edit, resolve depths, arrange, generate foam and Gridfinity outputs, export all formats, verify selected CAD dimensions, inspect STL in a slicer, manufacture one representative organizer, and record actual fit.

Automated artifacts may be produced first, but `v0.1.0` remains a GitHub pre-release until representative physical validation is recorded as passed.

## Packaging layout

Keep packaging mechanics separated from app modules, with dedicated PyInstaller, Inno Setup, release-helper, and manufacturing-validation files under a `packaging/` area.

## Pull-request Windows CI

Extend Windows CI to:
1. install dependencies;
2. run compile/import sanity checks;
3. run full pytest;
4. build the PyInstaller one-directory app;
5. run frozen self-test;
6. build the Inno Setup installer;
7. build the portable ZIP;
8. verify expected artifacts are nonempty;
9. compute SHA-256 hashes;
10. upload installer/portable/hash artifacts.

Packaging failure blocks merge.

## Tagged release workflow

A `v0.1.0`-style tag checks version consistency, reruns source and packaged verification, builds installer/portable artifacts from the tagged commit, creates `SHA256SUMS.txt`, and uploads them to a GitHub Release. The release starts as pre-release until physical validation is completed.

The workflow does not silently sign binaries. Authenticode is enabled only when certificate/secrets are deliberately configured later.

## Documentation

Document Windows x64 support, install/uninstall, portable use, offline/local-first behavior, diagnostics, unsigned-installer expectations, `.tds` V4 compatibility, manufacturing validation, V0.1 limitations, and reproducible bug reporting with version/log details.

## Explicit deferrals

Not part of this slice: multi-layer foam, printer-bed splitting, custom polygon drawers, cloud/account sync, inventory tracking, auto-updater, `.tds` file association, MSIX/Store packaging, mandatory signing, or telemetry.

## Acceptance gates

Merge only after fresh Windows CI proves source tests, frozen self-test, installer build, portable build, artifact upload, SHA-256 manifest, manufacturing fixture, unsaved-project tests, preferences tests, and deterministic logging tests. No unresolved review findings may remain. Record exact tested feature head and merge ref. Merge only after explicit user authorization.

After merge, creating the `v0.1.0` tag/release is a separate explicit action. Physical validation decides whether the release remains pre-release or is promoted to normal release.
