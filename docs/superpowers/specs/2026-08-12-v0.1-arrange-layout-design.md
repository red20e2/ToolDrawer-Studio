# ToolDrawer Studio V0.1 Arrange / Layout Design

**Date:** 2026-08-12  
**Status:** Approved conversational design, pending written-spec review  
**Branch:** `feature/v0.1-arrange-layout`  
**Base:** `main` at `8bff69770357369649ee77ff3973e7254b2abe39`

## 1. Goal

Add the V0.1 **Arrange** stage to ToolDrawer Studio so calibrated, traced, refined, and measured tools can be placed inside a real organizer boundary before Gridfinity or foam geometry is generated.

Arrange must support:

- rectangular foam/drawer/tray layouts using real inside dimensions;
- Gridfinity layouts defined primarily by columns × rows and grid pitch;
- one continuous usable Gridfinity organizer area, allowing tools to cross nominal cell boundaries;
- deterministic automatic packing using actual calibrated tool contours;
- practical-access-first scoring rather than density-only packing;
- manual drag, rotate, lock/unlock, multi-select, align/distribute, and re-pack-unlocked controls;
- optional snapping without forcing the user onto a grid;
- per-tool rotation restrictions;
- independent manufacturing clearance and structural layout spacing;
- optional per-tool grab-side access zones;
- valid partial layouts with clearly identified unplaced tools when everything cannot fit;
- persistent, editable layout state in `.tds` projects.

The Arrange stage sits in the existing workflow:

`Capture -> Calibrate -> Detect -> Refine -> Measure -> Arrange -> Generate -> Verify -> Export`

## 2. Scope Decisions

The following choices are approved for V0.1.

### 2.1 Boundary types

V0.1 supports **rectangular organizer boundaries only**.

- Foam/drawer/tray mode uses exact inside width × depth in millimetres.
- Gridfinity mode uses columns × rows as the primary input and shows calculated physical dimensions live.
- Custom polygon drawer boundaries are deferred.

### 2.2 Gridfinity behavior

Gridfinity arranging is included in V0.1.

The Gridfinity cell block is treated as **one continuous usable rectangular area**. A long ratchet, pliers, or other tool may cross nominal 42 mm cell boundaries. The Gridfinity cell structure constrains the later generated base, not individual tool placement.

Default Gridfinity pitch is **42.0 mm**. The layout model stores pitch explicitly so custom pitch remains possible without redesigning persistence.

Example:

- 6 columns × 5 rows × 42.0 mm pitch = **252.0 × 210.0 mm** overall layout area.

Actual usable cavity area may later be reduced by generator-specific walls or structural rules. Arrange V0.1 validates against its configured usable boundary and border margin; Generate remains authoritative for final Gridfinity solid geometry.

### 2.3 Rotation behavior

Automatic packing uses practical discrete angle candidates. Manual editing permits free rotation.

Each tool has one of three rotation policies:

- `free`: automatic packing tests 15° increments around a full turn; manual rotation may use any angle;
- `orthogonal`: automatic/manual snap candidates are 0°, 90°, 180°, and 270° relative to the tool's reference orientation;
- `fixed`: automatic packing preserves the current/reference orientation.

The UI may expose friendly labels **Free**, **90° only**, and **Fixed** while persistence uses stable enum-like values.

### 2.4 Packing priority

Automatic layout optimizes in this order:

1. geometric validity;
2. practical access;
3. orientation quality/consistency;
4. number of tools placed;
5. compactness/utilization.

The engine must never violate hard spacing or boundaries merely to improve utilization.

### 2.5 Grab-side access

Every tool uses general structural spacing. A tool may additionally define one optional grab side/end requiring extra access room.

Supported V0.1 grab-side values:

- `none`
- `left`
- `right`
- `top`
- `bottom`

The grab zone is a placement exclusion region derived from the oriented tool footprint and the configured extra access distance. It is a layout constraint, not pocket geometry. Finger scoops remain a Generate-stage concern.

### 2.6 Manual editing controls

V0.1 includes:

- drag selected tools;
- rotate selected tool(s);
- lock/unlock;
- multi-select;
- align left/right/top/bottom/centers;
- distribute horizontally/vertically;
- re-pack only unlocked tools;
- undo/redo for layout edits.

Persistent grouping as a first-class assembly object is deferred. Multi-selection provides the V0.1 move/rotate-together interaction without introducing a separate group lifecycle.

### 2.7 Snapping

Movement is free by default.

Optional snapping supports:

- Gridfinity grid lines;
- organizer edges;
- alignment with other tool anchors/edges;
- configurable movement increment.

Snapping changes interaction only. Stored placement values remain canonical millimetres and are not rounded unless the chosen snap operation explicitly produces the rounded position.

### 2.8 Collision geometry

Packing and validation use the **actual calibrated tool contours**, not rectangular bounding boxes.

Each collision footprint is derived from:

1. the edited tool contour;
2. manufacturing pocket clearance, applied only when determining the eventual cavity footprint if requested by Generate;
3. **layout structural spacing**, which is separate and applied specifically for Arrange collision/exclusion tests;
4. optional grab-side access exclusion.

V0.1 Arrange must not substitute a pixel-raster collision mask for final validity. Geometry tests operate in millimetres.

### 2.9 Spacing defaults

Project defaults are configurable and persisted. Initial defaults:

- minimum tool-to-tool structural spacing: **3.0 mm**;
- outer border margin: **4.0 mm**;
- extra grab-side access distance: **12.0 mm**;
- manual movement snap increment: **1.0 mm**.

These are defaults, not hard-coded manufacturing rules.

Tool pocket clearance remains the existing per-tool manufacturing value and is not reused as the structural tool-to-tool spacing setting.

### 2.10 Failure to fit

If every requested tool cannot fit, automatic packing returns the **best valid partial layout**.

The system must:

- retain all valid placements found;
- identify each unplaced tool explicitly;
- never overlap tools, violate borders, or reduce required spacing silently;
- allow the user to resize, move, remove, lock/unlock, or re-pack afterward.

### 2.11 Locked placements

Locked tools preserve **exact position and rotation** across Auto Arrange / Re-pack Unlocked operations.

If a locked tool becomes invalid because the user shrinks the boundary or increases spacing, the layout is marked invalid. The application must not silently move the locked tool.

## 3. Architecture

Arrange is split into focused geometry, packing, validation, controller, persistence, and Qt presentation layers.

Recommended package structure:

```text
src/tooldrawer_studio/
  layout/
    __init__.py
    models.py
    geometry.py
    validation.py
    scoring.py
    packer.py
  ui/
    arrange_panel.py
    arrangement_view.py
```

Existing `WorkflowController` remains the mutation authority for project state. Qt widgets request mutations through controller methods rather than directly editing domain objects.

### 3.1 Geometry library

Use **Shapely 2.x** for robust 2D polygon buffering, rotation, intersection, containment, and distance operations in real-world millimetres.

Reasons:

- it avoids resolution-dependent pixel-mask collision decisions;
- it provides deterministic polygon operations suitable for irregular calibrated contours;
- Windows wheels are available, so it does not require users to compile GEOS;
- packing can run much faster than repeatedly invoking full OpenCascade solids.

CadQuery/OpenCascade remains authoritative for generated manufacturing solids. Shapely is the Arrange-stage 2D geometry engine only.

The dependency must be version-bounded in `pyproject.toml` and exercised on Windows CI.

## 4. Canonical Layout Coordinate System

All persistent layout coordinates are millimetres.

Use a right-handed 2D organizer coordinate system:

- origin `(0, 0)` is the lower-left corner of the full rectangular organizer boundary;
- +X moves right;
- +Y moves up;
- rotation is degrees counter-clockwise.

Qt scene coordinates may use +Y downward internally, but conversion occurs only at the presentation boundary. Persistence and packing never store Qt pixel coordinates.

### 4.1 Tool local geometry

A tool's existing `contour_mm` remains unchanged and continues to represent calibrated source geometry.

For Arrange calculations, derive a local polygon and stable layout anchor from the contour:

- validate/repair the polygon if necessary using bounded deterministic geometry cleanup;
- compute a stable centroid anchor;
- translate the working polygon so the anchor is local `(0, 0)`;
- rotate around that local anchor;
- translate to the placement's stored `(x_mm, y_mm)`.

The source contour is never rewritten merely because the tool is arranged.

## 5. Domain Model

Persistence moves from `.tds` schema V2 to **schema V3**.

### 5.1 Project layout defaults

Add project-level persisted fields conceptually equivalent to:

```python
default_layout_spacing_mm: float = 3.0
default_layout_border_mm: float = 4.0
default_grab_clearance_mm: float = 12.0
default_snap_increment_mm: float = 1.0
gridfinity_pitch_mm: float = 42.0
layout: LayoutState | None = None
```

Exact class/file organization may follow existing domain conventions, but serialized names and migration rules must be explicit and tested.

### 5.2 LayoutState

`LayoutState` contains:

- mode: `foam` or `gridfinity`;
- width_mm;
- height_mm;
- Gridfinity columns/rows when in Gridfinity mode;
- Gridfinity pitch;
- structural spacing;
- border margin;
- default grab clearance;
- snap settings;
- tool placements;
- current unplaced tool IDs;
- validity/review state sufficient to restore UI without automatically repacking.

For Gridfinity mode:

```text
width_mm  = columns * pitch_mm
height_mm = rows * pitch_mm
```

The serialized dimensions may be stored redundantly only if validation enforces exact consistency. Prefer deriving them from rows/columns/pitch when loading Gridfinity mode to prevent contradictory state.

### 5.3 ToolPlacement

Each placement stores:

- `tool_id`;
- `x_mm`;
- `y_mm`;
- `rotation_deg` normalized to `[0, 360)`;
- `locked`;
- `rotation_policy`;
- `grab_side`;
- optional per-tool `grab_clearance_override_mm`;
- `is_placed`.

A tool appears at most once in one V0.1 layout.

### 5.4 Layout validity

Do not persist a bare `is_valid=True` as trusted truth across arbitrary edits. Validity is computed from the current domain state.

The project may persist a lightweight `layout_review_required` flag to communicate that dimensions/geometry changed since the user's last accepted arrangement, but opening a project must perform cheap deterministic validation before Generate may consume the layout.

## 6. Schema V2 -> V3 Migration

Migration must be non-destructive.

For a V2 project:

- preserve every capture, calibration, trace, refinement, side-view measurement, accepted thickness, and pocket-depth value exactly;
- add the V3 layout defaults;
- set `layout = None`;
- do not invent placements;
- do not alter existing tool contours or dimensions;
- save migrated projects as V3 on the next explicit save;
- continue rejecting unknown future schema versions.

Migration must be covered by exact-value round-trip tests.

## 7. Arrange Stage UI

Insert **Arrange** after Measure in the existing main workflow.

### 7.1 ArrangePanel

The side/control panel contains:

- layout mode selector: Foam/Drawer or Gridfinity;
- Foam width and depth inputs;
- Gridfinity columns and rows inputs;
- Gridfinity pitch display/input;
- live calculated physical Gridfinity width × height;
- structural spacing;
- border margin;
- default grab clearance;
- snap enable/options and increment;
- Auto Arrange;
- Re-pack Unlocked;
- selected-tool rotation policy;
- selected-tool grab side;
- optional per-tool grab-clearance override;
- lock/unlock;
- rotate controls;
- align/distribute controls;
- placed/unplaced status summary;
- validation warnings.

The panel must make clear that **layout spacing is not pocket clearance**.

### 7.2 ArrangementView

The central view displays:

- organizer boundary;
- border/usable boundary;
- optional Gridfinity cell lines as visual guides;
- real tool outlines at their current placement and rotation;
- selected/multi-selected state;
- grab access regions;
- locked state;
- collision/boundary invalid overlays;
- unplaced-tool tray/list.

Gridfinity cell lines are guides, not individual containment boundaries.

### 7.3 Manual interactions

Drag:

- previews movement continuously;
- applies optional snapping;
- shows collision/boundary feedback before commit;
- commits one undoable command on mouse release rather than flooding undo history for every mouse move.

Rotate:

- free tools permit arbitrary manual angle;
- 90° tools snap to orthogonal angles;
- fixed tools reject manual rotation unless the user first changes the rotation policy.

Multi-select:

- supports marquee or modifier selection;
- movement/rotation preserves relative placement of selected items;
- validation occurs for the whole transformed selection;
- V0.1 does not create a persistent group object.

Lock:

- locked items cannot be dragged or rotated until unlocked;
- packing treats them as fixed obstacles.

## 8. Deterministic Packer

Implement a deterministic geometry-aware heuristic packer rather than a genetic or stochastic optimizer in V0.1.

### 8.1 Inputs

- usable rectangular boundary after border margin;
- tool local polygons;
- structural spacing;
- grab exclusion geometry;
- current placements;
- locked placements;
- rotation policies;
- deterministic project/tool ordering.

### 8.2 Hard constraints

A candidate is invalid if:

- its tool footprint or required exclusion region crosses the usable boundary;
- it intersects another tool's required exclusion geometry;
- it modifies a locked tool;
- it violates the tool's rotation policy;
- its numeric geometry contains NaN/inf or invalid polygon data.

Hard constraints are never weakened automatically.

### 8.3 Tool ordering

Pack difficult tools first. Use a deterministic sort key based on stable geometry metrics and tool ID as final tie-breaker.

Priority should favor:

1. fixed/restricted rotation tools;
2. larger maximum dimension;
3. larger footprint area;
4. irregular/low-placement-flexibility geometry where cheaply measurable;
5. stable tool ID tie-break.

The exact weighting belongs in the implementation plan and must be covered by deterministic tests.

### 8.4 Candidate rotations

For automatic packing:

- Free: 0°, 15°, 30° ... 345° relative to reference orientation;
- 90° only: 0°, 90°, 180°, 270°;
- Fixed: current/reference angle only.

Equivalent rotations for symmetric geometry may be deduplicated as an optimization, but deduplication must not change correctness.

### 8.5 Candidate positions

Avoid brute-forcing every fractional millimetre across the entire drawer.

Generate candidate positions deterministically from useful geometric events such as:

- usable-boundary corners/edges;
- vertices/bounds of already placed exclusion polygons;
- spacing offsets from placed items;
- optional coarse seed lattice followed by local refinement where justified.

The implementation plan must benchmark candidate growth to prevent pathological UI stalls.

### 8.6 Scoring

Packing scoring is lexicographic or strongly weighted so a lower-priority improvement can never compensate for invalidity.

Recommended score order:

1. valid placement count;
2. access quality, including grab-zone obstruction penalties;
3. orientation consistency / unnecessary-angle penalty;
4. occupied bounding-box compactness;
5. total unused/wasted area approximation;
6. stable deterministic tie-break based on tool/order/coordinates.

For a single candidate position of one tool, validity is a prerequisite before scoring.

### 8.7 Auto Arrange vs Re-pack Unlocked

**Auto Arrange**:

- preserves locked tools;
- repacks all unlocked tools;
- may move currently placed unlocked tools;
- returns best valid placement set and explicit unplaced list.

**Re-pack Unlocked** follows the same rule and exists as the user's explicit command after manual locking/positioning.

Neither command changes locked placements.

### 8.8 No silent rearrangement

Changing layout dimensions, spacing, grab clearance, or tool geometry does **not** automatically rearrange tools.

Instead:

- recompute validity;
- mark/report conflicts;
- require the user to invoke Auto Arrange/Re-pack Unlocked or repair manually.

This preserves user intent and makes undo/redo comprehensible.

## 9. Validation Service

`LayoutValidationService` validates a restored or edited layout independently from the packer.

It returns structured issues, not just a boolean.

Issue types include:

- missing tool reference;
- duplicate placement;
- invalid polygon;
- boundary violation;
- tool overlap/spacing violation;
- grab-zone obstruction;
- invalid locked placement;
- rotation-policy violation;
- invalid Gridfinity dimensions/pitch;
- unplaced tool.

Generate must refuse to consume a layout containing hard geometry errors. Unplaced tools are allowed as an Arrange state but must be explicitly acknowledged/handled before generating an organizer intended to contain all project tools.

## 10. Geometry and Spacing Semantics

Manufacturing and layout concepts remain distinct:

- **Tool pocket clearance**: per-tool cavity fit allowance, currently stored on `ToolObject`.
- **Layout spacing**: minimum structural material/access separation between neighboring planned cavities.
- **Border margin**: minimum planned distance from tool/cavity exclusion geometry to the organizer boundary.
- **Grab clearance**: additional space reserved on a selected side to support removal/access.

The Arrange view may preview the effective exclusion envelope, but it must not mutate the source contour to create that envelope.

When Generate later creates actual solids, it must revalidate that its wall/base geometry can realize the requested Arrange spacing. Arrange is not permitted to claim final manufacturability for a Gridfinity shell it has not generated yet.

## 11. Undo / Redo

Continue the existing Qt undo-stack pattern.

Undoable operations include:

- move;
- rotate;
- multi-move/multi-rotate;
- lock/unlock;
- rotation-policy change;
- grab-side/override change;
- align;
- distribute;
- Auto Arrange/Re-pack as one compound command;
- relevant layout setting changes when they mutate persisted project state.

A drag gesture is one command. An automatic pack operation is one command, regardless of how many tools moved.

## 12. Persistence and Reopen Behavior

Saving a `.tds` project persists the exact Arrange state.

Reopening must:

- restore mode, dimensions, pitch, defaults, placements, rotation, lock state, grab settings, and unplaced state;
- restore the layout without invoking the auto-packer;
- run deterministic validation;
- show any conflicts/review requirement;
- preserve exact placement coordinates within normal JSON floating-point round-trip limits.

No automatic optimizer run may occur simply because a project was reopened.

## 13. Stale-State Rules

Changes upstream of Arrange can invalidate a layout.

### 13.1 Tool contour changes

If a tool's refined contour changes:

- preserve its placement position/rotation/lock state;
- recompute its layout footprint;
- validate the full layout;
- mark review required if a conflict appears;
- do not move the tool automatically.

### 13.2 Tool addition/removal

New tool:

- create an unplaced layout entry/default placement metadata as needed;
- existing placements remain unchanged.

Removed tool:

- remove its placement from layout state;
- leave all other placements unchanged.

### 13.3 Measurement/depth changes

Thickness/pocket-depth changes do not alter the 2D Arrange footprint in V0.1, so they do not trigger repacking. Generate may still reject impossible vertical geometry later.

### 13.4 Boundary/spacing changes

Preserve placements, recompute validity, and require explicit user action to repack.

## 14. Error Handling

User-facing failures must be specific and recoverable.

Examples:

- invalid/non-positive width, depth, pitch, spacing, or margin;
- Gridfinity rows/columns less than 1;
- border margin leaves no usable area;
- tool contour cannot form a usable polygon;
- locked tool lies outside the new boundary;
- packer cannot place one or more tools;
- layout contains stale/missing tool IDs after corrupted/manual project editing.

The application must never silently drop a tool from the project because Arrange cannot place it.

Unexpected geometry exceptions must be caught at the service/controller boundary, surfaced as an Arrange error, and leave the previous valid project state intact.

## 15. Performance Requirements

V0.1 is a desktop interactive workflow, not an offline batch optimizer.

Targets on a normal modern Windows workstation:

- manual drag/rotate feedback should feel interactive for typical shop layouts;
- validation of approximately 25 tools should complete fast enough to update after an edit without perceptible multi-second blocking;
- automatic packing of approximately 25 ordinary tool outlines should target completion within a few seconds rather than minutes;
- the UI must remain responsive during longer pack operations.

If the heuristic can exceed a short interactive budget, execute packing outside the Qt GUI thread with cancellation support, while project mutation remains serialized through the controller.

The implementation plan must include performance fixtures/benchmarks sufficient to catch obvious candidate-explosion regressions without creating brittle timing tests in shared CI.

## 17. Acceptance Criteria

Arrange V0.1 is complete only when all of the following are true:

1. A user can create a rectangular foam/drawer layout in millimetres.
2. A user can create a Gridfinity layout by columns × rows with live calculated dimensions.
3. Tools may span Gridfinity cell boundaries.
4. Real contour polygons drive collision/spacing validation.
5. Manufacturing pocket clearance and structural layout spacing remain separate.
6. Auto Arrange is deterministic.
7. Auto Arrange respects Free/90°/Fixed policies.
8. Locked tools never move during repacking.
9. Grab-side access exclusions are respected.
10. Auto Arrange optimizes valid practical layouts before density.
11. Failure to fit returns valid placements plus explicit unplaced tools.
12. Manual drag/rotate/lock/multi-select/align/distribute works with undo/redo.
13. Snapping is optional and free movement remains available.
14. Re-pack Unlocked does not move locked tools.
15. Setting/geometry changes never silently rearrange the layout.
16. `.tds` V3 persists/reopens the exact layout without auto-repacking.
17. V2 projects migrate non-destructively.
18. Hard-invalid layouts cannot silently feed Generate.
19. Windows CI passes the complete suite.
20. No Gridfinity solid generation or foam manufacturing export is smuggled into this slice.

## 18. Explicitly Deferred

The following are out of scope for Arrange V0.1:

- custom polygon/non-rectangular drawer boundaries;
- stochastic/genetic/global optimization;
- persistent tool groups/assemblies;
- automatic semantic detection of the best grab side;
- actual Gridfinity base/body solid generation;
- foam layer generation;
- finger-scoop solid generation;
- labels/magnets/screw holes;
- stepped-depth region editing;
- multi-view/3D geometry;
- AI-based layout suggestions;
- direct slicer/CNC handoff changes.

Those belong to later Generate/library/advanced slices unless a focused requirement explicitly pulls them forward.

## 19. Recommended Implementation Approach

Use the deterministic geometry-aware heuristic approach approved during design.

Do **not** implement a stochastic optimizer in V0.1. The deterministic engine gives ToolDrawer Studio:

- reproducible projects;
- testable packing behavior;
- understandable undo/redo;
- predictable support/debugging;
- a clean baseline for adding an optional heavier optimizer later.

The next implementation artifact after this written spec is approved is a task-by-task TDD implementation plan under `docs/superpowers/plans/`.
