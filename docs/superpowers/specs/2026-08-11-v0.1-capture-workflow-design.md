# ToolDrawer Studio V0.1 Capture Workflow Design

**Date:** 2026-08-11  
**Status:** Approved design  
**Repository:** `red20e2/ToolDrawer-Studio`  
**Target branch:** `feature/v0.1-capture-workflow`

## 1. Purpose

This slice expands ToolDrawer Studio's image capture workflow beyond file import while preserving the local-first, offline-capable product architecture.

V0.1 capture will support:

- Windows webcam capture with live preview and camera selection.
- Phone-to-PC photo transfer over the local network using a QR-code session.
- Multiple phone uploads per QR session.
- One shared pending-capture tray for webcam and phone images.
- Explicit promotion of selected pending images into the project through **Add to Project**.

The capture workflow must reuse the existing image validation, calibration, project persistence, and tracing pipeline rather than introducing parallel image-handling rules.

## 2. User Workflow

### 2.1 Phone capture

1. User selects **Start Phone Session**.
2. ToolDrawer Studio starts a temporary LAN-only upload endpoint.
3. A cryptographically random session token is generated.
4. The desktop app displays a QR code containing the temporary local upload URL and token.
5. The phone opens a minimal local web page with:
   - **Take Photo**
   - **Choose Existing Photo**
6. The user may upload multiple photos during the same session.
7. Valid uploads appear in the shared pending-capture tray.
8. The user may preview, rotate, delete, or select pending images.
9. **Add to Project** promotes the selected pending image into the normal project capture flow without removing unrelated pending images.
10. The phone session remains active until the user presses **Stop** or the session reaches the idle timeout.

### 2.2 Webcam capture

1. User opens the webcam capture panel.
2. Available cameras are enumerated.
3. User selects a camera.
4. ToolDrawer Studio shows a live preview.
5. User presses **Capture**.
6. The captured still is validated through the same image-safety path as other inputs.
7. The image appears in the shared pending-capture tray.
8. The user may preview, rotate, delete, select, and **Add to Project**.

## 3. Approved UX Decisions

The following choices are fixed for this slice:

1. One phone QR session accepts multiple photos.
2. Phone and webcam captures share one pending tray.
3. Pending images do not automatically replace the active project image.
4. Phone sessions use manual **Stop** plus a 30-minute inactivity timeout.
5. The phone page supports both taking a new photo and choosing an existing photo.
6. Webcam capture provides live preview, camera selection, and a Capture button.
7. **Add to Project** promotes only the selected pending image and keeps the other pending captures available.
8. Pending tray contents are temporary application-session data for V0.1. Crash recovery for unpromoted pending captures is out of scope.

## 4. Architecture

The capture implementation will be split into isolated components with explicit responsibilities.

### 4.1 `CaptureSessionService`

Responsibilities:

- Own pending captures from all transient capture sources.
- Assign stable pending-capture identifiers.
- Store source type and capture metadata.
- Add, select, rotate, delete, and enumerate pending captures.
- Promote selected pending captures into the existing project capture pipeline.
- Keep promotion logic separate from UI widgets.

Dependencies:

- Existing image loader/validation functions.
- Existing project/workflow controller integration point.

### 4.2 `WebcamCaptureService`

Responsibilities:

- Enumerate available webcam devices.
- Open and release the selected device safely.
- Produce live preview frames.
- Capture a still frame on request.
- Convert the captured still into a normal validated capture input.
- Surface camera disconnect and capture failure cleanly.

The service must not require a physical camera in automated tests; device access will be abstracted so tests can use mocks/fakes.

### 4.3 `PhoneUploadServer`

Responsibilities:

- Start only when the user explicitly starts a phone session.
- Bind only to the selected private/local IPv4 interface chosen for the active LAN session. It must not intentionally expose an internet-facing listener; if no suitable local interface can be resolved, session start fails closed.
- Generate a fresh cryptographically random token per session.
- Serve the minimal upload page with no third-party scripts, fonts, images, analytics, or other external resources.
- Accept multiple authenticated image uploads in one active session.
- Enforce request and image safety limits.
- Track authenticated session activity.
- Stop on manual request or after 30 minutes of inactivity.
- Invalidate the current token when stopped.
- Release its listening socket when ToolDrawer Studio exits.

A small embedded HTTP implementation is preferred over adding a full web application framework unless implementation evidence shows a compelling reason otherwise.

### 4.4 `CaptureTray` UI

Responsibilities:

- Present pending captures from both phone and webcam sources.
- Show preview/thumbnail and source metadata.
- Allow selection.
- Allow 90-degree rotation in the pending working copy.
- Allow deletion.
- Provide **Add to Project**.
- Preserve unrelated pending captures after one item is promoted.

The tray must not own persistence or image validation logic.

## 5. Data Model

A pending capture is transient and separate from the persistent project `CaptureAsset` until promoted.

Conceptual fields:

- `id`
- `source` (`phone` or `webcam`)
- `filename` or generated capture name
- `captured_at`
- validated working image
- original uploaded/captured bytes where applicable
- rotation state in 90-degree increments

Promotion converts a pending capture into the existing project capture representation through one central path.

If the user rotates a pending image before promotion, ToolDrawer Studio applies that rotation to the promoted source image. The promoted, user-approved orientation becomes the project's canonical capture asset. Unmodified pending source bytes remain transient and need not be stored separately after promotion. This avoids adding a second persistent orientation model solely for the tray.

No second project-image schema should be created for webcam or phone images.

## 6. Data Flow

### Phone

`Start Phone Session -> token + LAN URL -> QR -> phone page -> upload -> validate -> pending tray -> preview/rotate/delete -> Add to Project -> existing project capture flow`

### Webcam

`Open Webcam -> select device -> live preview -> Capture -> validate -> pending tray -> preview/rotate/delete -> Add to Project -> existing project capture flow`

### Promotion rule

Promotion must reuse the existing image-loader and workflow-controller behavior so calibration, normalized display, tracing, and `.tds` persistence continue to operate on one canonical image model.

## 7. Session Lifecycle

### 7.1 Start

- Starting a phone session creates a new token and endpoint state.
- Old tokens are never reused.
- The desktop UI displays the corresponding QR code and session status.

### 7.2 Active session

- Multiple images may be uploaded.
- An authenticated load of the local upload page or a successfully accepted upload refreshes the 30-minute inactivity timer.
- Invalid-token requests, malformed requests, rejected uploads, and unrelated network traffic do not refresh the timer.
- The desktop may continue using webcam capture independently while the phone session is active.

### 7.3 Stop

A session stops when:

- the user presses **Stop**,
- 30 minutes pass without authenticated page activity or a successfully accepted upload,
- the application exits,
- or the server encounters an unrecoverable bind/runtime failure.

Stopping the session must:

- close the listening socket,
- invalidate the token,
- make the previous QR URL unusable,
- update the desktop UI state,
- leave already accepted pending captures intact.

## 8. Security and Network Boundary

The LAN upload feature must expose the smallest practical attack surface.

Requirements:

1. No cloud relay or internet dependency.
2. No account or authentication service.
3. Fresh cryptographically random token per session.
4. Token required to load/use the upload session.
5. Old token invalid immediately after Stop/restart/expiry.
6. Accept image uploads only.
7. Do not accept arbitrary filesystem paths from clients.
8. Do not expose project files, local folders, shell commands, or arbitrary download endpoints.
9. Serve no third-party page resources that could leak the temporary session URL/token through browser requests.
10. Apply existing maximum image limits:
    - 50 MB source bytes.
    - 40 megapixels decoded image size.
11. Reject corrupt, unsupported, oversized, or invalid images before they enter the pending tray.
12. Incomplete uploads must not create pending items.
13. Closing ToolDrawer Studio must always stop the server and release webcam handles.
14. Failure to identify a suitable private/local IPv4 address must prevent the phone session from starting rather than broadening the bind automatically.

V0.1 assumes the phone and PC are on the same local network. Remote internet access, relay, NAT traversal, and cloud upload are explicitly out of scope.

## 9. Error Handling

### Webcam

- Device disappears: stop preview cleanly and present the remaining available cameras when possible.
- Device open fails: show a clear capture error and leave pending data unchanged.
- Still capture fails: do not add a pending item.

### Phone upload

- Server bind fails: do not show a usable QR session; report the failure.
- No suitable private/local IPv4 interface: fail session startup and explain that phone and PC must share a usable local network.
- Invalid token: reject the request.
- Expired/stopped session: phone page reports that the session has ended when possible; otherwise the closed endpoint is simply unreachable.
- Upload interrupted: discard incomplete data.
- Invalid or oversized image: reject without modifying the existing tray.
- Network address changes during an active session: current session is stopped and a new session must be started to generate a fresh URL.

### Application shutdown

- Stop active phone server.
- Invalidate token.
- Release webcam handles.
- Do not block application exit waiting on abandoned network clients.

## 10. Testing Strategy

### Unit/service tests

- Token is required.
- Incorrect token is rejected.
- Old token fails after Stop.
- Old token fails after starting a replacement session.
- 30-minute inactivity expiration works deterministically with an injectable/mockable clock.
- Authenticated upload-page activity refreshes the timer.
- Successful accepted upload refreshes the timer.
- Invalid/rejected traffic does not refresh the timer.
- One active session accepts multiple valid uploads.
- Valid uploads produce pending captures.
- Oversized byte payload is rejected.
- Excessive decoded pixel count is rejected.
- Invalid/non-image payload is rejected.
- Interrupted/partial upload does not produce a pending item.
- No suitable private/local interface fails closed.
- Served upload page contains no third-party resource references.
- Webcam enumeration uses an abstracted/mockable backend.
- Webcam capture success creates a pending capture.
- Webcam capture failure creates nothing.
- Phone and webcam captures use the same pending-capture model.
- Rotate/delete/select operate on the intended pending item.
- Rotating a pending image changes the promoted canonical image orientation without modifying unrelated pending items.
- **Add to Project** promotes exactly the selected item.
- Promoting one item does not delete unrelated pending captures.

### Integration/UI tests

- Existing import/calibration workflow still works.
- Promoted phone image can be calibrated and traced.
- Promoted webcam image can be calibrated and traced.
- Opening/saving/reopening `.tds` projects continues to work for promoted captures.
- UI session state correctly reflects start, active, expired, stopped, and failure states.
- Existing regression suite remains green.

### CI requirement

The Windows GitHub Actions suite must pass before the capture slice is considered complete.

## 11. Dependency Policy

This slice should avoid unnecessary framework weight.

- Reuse PySide6 and OpenCV already present in the application.
- Prefer a small embedded HTTP implementation for the upload server.
- QR generation may add a focused dependency if needed, but dependency choice must be verified during implementation planning.
- Special HEIC decoding support is not part of this slice unless the existing image stack already handles it without new native dependencies.

Any new Windows/native dependency must be justified against install size, CI reliability, licensing, and offline operation.

## 12. Out of Scope

The following are deliberately deferred:

- Cloud upload or remote relay.
- User accounts.
- Internet-accessible capture sessions.
- Permanent background upload service.
- Automatic crash recovery of unpromoted pending tray images.
- Advanced multi-view association semantics such as automatically classifying top/side/angled views.
- Side-view thickness estimation itself.
- Special HEIC codec integration requiring new native dependencies.
- Local AI tracing changes.
- Layout/Gridfinity/foam work.

The capture architecture must nevertheless leave room for future top/side/angled image association by allowing multiple promoted capture assets in a project.

## 13. Acceptance Criteria

This design slice is complete when a Windows user can:

1. Select a webcam, see a live preview, capture multiple stills, and see them in the shared tray.
2. Start a LAN phone session, scan a QR code, take or choose multiple phone images, and see them appear in the same tray.
3. Rotate, delete, select, and preview pending images.
4. Add one selected pending image to the project without losing the others.
5. Stop the phone session manually and verify the old URL/token no longer works.
6. Allow an inactive session to expire after 30 minutes under the defined authenticated-activity rules.
7. Promote either source into the existing calibration/tracing/project workflow.
8. Close the app without leaving a phone server or webcam device open.
9. Pass the full Windows automated test suite.
